## 3. 当前代码与账本给出的证据

- [runtime.py](../../entropy_arb/v3/runtime.py)：第一腿正成交后处理实际对冲量，权威仓位对账，部分关闭后的残量配平和重新判断退出。

- [retro_farming.py](../../entropy_arb/retro_farming.py) 与 [既有架构说明](../../ARBITRAGE_ARCHITECTURE.md)：已有项目贡献、奖励假设与现金成本区分。不要重新发明“积分盈利”。

### 真实缺口及其限定

1. `core.plan_open` 明确是 **回到当前 reference 的场景检查，不是统计期望收益模型**。入场带宽仍是固定 bps；动态中线不证明回归发生的概率和时间。
2. `Settings.execution_allowance_bps` 是固定余量；价格 ladder/hard cap 是订单容许边界，不是每次实际付出的成本。应该用实测、分条件执行损耗做研究，而不是把最大滑点直接当作预期费用。
3. 资金费在 `runtime._reconcile_cycle_accounting` 的最终账务里计入；当前 `plan_open` 不预估持有期间资金费，活动退出与风险估值也没有独立的实时 funding 输入。跨结算点、长持仓时需研究其影响。不能把“最终已计费”误写成“入场和持有决策已计费”。
4. `book.is_fresh` 主要检验连接活性；`feeds.py` 已检查 Lighter nonce 缺口并重新取快照。仍需区分正常静默与“连接活着但盘口失真”，不能简单按无价格变化秒数拒绝安静市场。
5. 目前 pair 建立主要靠精确 symbol、线性 base quantity 约定与精度。扩展 hedge venue 前，应明确核对合约乘数、结算币种、oracle、交易时段和停牌规则；同名合约不自动等价。
6. 初次评估时工作区与最近部署 release 的 runtime 分别为 2,240 行和 2,704 行。2026-10-04 已将 `.releases/entropy-edge-v2-strategy-risk-20260924` 的 V3 核心、入口、适配器与相关工具整合回工作区，核心源码逐文件哈希一致，并保留工作区独有功能；合并范围与验证见 [源码基线记录](../../tasks/todo.md#2026-10-04--v3-source-baseline-unification)。源码统一不等于部署切换，最近保存的 live effective manifest 仍指向原 release。
7. release 已有后台账务补全、handoff 期间遥测延后和 close group 等修复，本次已连同回归测试纳入工作区。因此“把遥测移出跨腿路径”不是全新缺失能力；后续职责拆分应以这一统一源码基线为起点。旧状态文件只能说明当时加载的版本，不能证明今天进程正在运行。

## 4. 建议的优化顺序

### P0：用现有数据证明机会，而不是先增加复杂度

先固定一个代码/配置版本和 SNDK pair，按方向与少量有意义的市场条件对比完整闭环。先研究美股开盘附近、常规时段与休市时段是否不同，不先铺几十个稀疏分组。

每个机会至少看：可执行入场价差、冻结入场基准后的回归路径、到两腿配平的损耗、回归等待时间、最终费用/资金费、恢复损失、未完成仓位的可执行估值和资金占用时间。中线随行情移动不等于已有仓位的盈利目标兑现。

复用 `v3_opportunities.py` 的时间顺序校准、训练和验证边界。补齐真实授权 cap 与数据/执行版本关联后再运行候选对比。没有反事实排队和成交信息时，IOC 回放仍是场景估计；maker 更不能假定触价即成交。

收益判断口径：

```text
完整闭环的预期现金收益
  = 预期可成交价差变化收益
  - 四腿实际费率对应的费用
  - 报价之外的增量执行损耗
  + 有符号资金费净现金流
  - 资金占用成本
```

如果已经用可成交 bid/ask 深度计算收益，不再额外重复扣同一份盘口点差或深度冲击。返佣已到账现金可以独立合并评估；未到账奖励、积分和短期年化不能使负现金策略变成已验证正 EV。

验收：相同版本下的样本外完整收益、恢复/未完成仓位和不确定性一起报告；提高入场阈值、提高胜率或降低每千美元磨损都不能单独作为成功标准。不能凭当前小样本宣布新参数可实盘盈利。

### P1：按尾延迟和风险状态改善执行

- 复用现有单调时钟遥测，将决策到发送、发送到首成交观察、首成交观察到 hedge 发送、hedge 到配平分别观察；区分同一 clock session，展示 P50/P95/P99 和缺失率。
- 将短期波动、盘口深度与跨腿损耗联结，验证什么条件下原有 1 bps execution allowance 不足。优化本地阻塞前先确认哪一段实际主导损失。
- 第一腿有可信成交即按增量/累计去重结果承担真实 hedge 义务。UNKNOWN 不能当作零成交、换 ID 重发；减少等待不能删掉持久化与仓位证据。
- 开仓机会过期可以放弃；已经打开的风险必须在合法限频和价格边界内完成对冲或 reduce-only 恢复。不能用同一个盈利过滤器阻塞两者。
- maker 作为后续小范围研究，不默认替换 taker。比较净费用节省、成交概率、成交后不利价格变化、撤单时迟到成交和真实 hedge 损耗，而不是只看 maker 费率。

验收：重跑已有部分成交、迟到重复成交、UNKNOWN、重启、撤单后成交和 reduce-only 场景；在低波动/高波动条件下比较尾延迟与现金损耗。不能用简单并发 `gather()` 跳过双 pending 恢复设计。

### P1：区分资金费、保证金与异常盘口风险

- 对持有周期跨结算点的机会，增加只读资金费结算时间/方向的研究输入，分开记录已结算现金、已累积但未结算费用和未来估计，避免重复计费。
- 在每个场所独立测保证金安全余量与可减仓性，不能以净 delta 为零推断不会单边清算。
- 用现有仓位恢复路径验证 ADL/外部平仓/人工错单，不增加另一套直接发单的 watchdog。
- 对维护、nonce 缺口、REST/WS 盘口差异和异常 oracle/mark 偏离进行只读诊断。REST 检查低频并遵守共享请求预算，不能每个 tick 双重轮询。

风险预算目前主要停新开仓，不自动定义全部活动仓位的强平策略。若以后增加持仓时间上限或风险退出，需单独明确其损失边界，并证明不会重现早先时间到强退兑现暂时浮亏的问题。

### P2：统一版本后，做有限的 runtime 职责拆分

先把部署 release 已验证的修复与工作区统一到一个明确基线，逐项保留用户未提交改动，不直接整文件覆盖。之后才考虑把 `runtime.py` 内部的三类职责分清：

1. 行情、仓位和订单证据获取。
2. 单个 cycle 的状态推进和唯一发单所有权。
3. 后台账务补全、遥测和展示投影。

`core.py` 的纯计算、现有 Journal、订单 ID、状态语义和数据库保持不变。允许复用已存在的后台任务与小函数；不为文件长度建立插件系统、事件总线或第二套账本。必须落盘的订单事实不能改为 best-effort 遥测。

验收重点是行为不变：首腿部分成交后的 hedge 数量、关闭后平衡残量回 OPEN、同 ID UNKNOWN 恢复、重启状态，以及遥测写入失败不阻塞必要对冲。先做这些特征测试，不以新增模块数衡量重构成果。

### P3：仅在 SNDK 数据证明必要时扩展路由或奖励分析

当前以 SNDK 为项目范围，不因作者做 BTC/ETH、韩股/ADR 或多交易所策略就扩展标的。先用只读数据比较真正支持相同 SNDK 合约的 hedge 场所；核对访问资格、合约语义、实际费率、流动性、保证金与恢复能力后再讨论发送器接入。

沿用现金账、已确认激励与回溯假设账分离。不要把自成交、关联账户互刷、机械对倒或不确定的积分权重作为优化方向；不要通过路由或网络部署绕过交易所访问限制。

## 5. 本轮核对的官方规则

以下页面于 2026-10-04 读取；最终使用仍以目标账户、网络、市场和交易所当时返回的规则为准。

- [Lighter Trading Fees](https://docs.lighter.xyz/trading/trading-fees) 与 [Account Types](https://apidocs.lighter.xyz/docs/account-types)：Standard 表列 maker/taker 0 费率、taker 300 ms；Premium 无质押表列 taker 140 ms、maker 0.0040% / taker 0.0280%。因此切换高级账户不是无成本提速，两次 taker 的表列费用已达 5.6 bps，须先验证是否有足够收益补偿。本轮未查询或修改项目账户等级；这些参数不套用于独立的其他网络。
- [Hyperliquid Fees](https://hyperliquid.gitbook.io/hyperliquid-docs/trading/fees)：HIP-3 growth mode 会降低协议费用、rebate 和 volume contribution；手续费仍受账户与市场配置影响。作者历史返佣、项目配置和实际 fill fee 不能互相替代。
- [Hyperliquid Funding](https://hyperliquid.gitbook.io/hyperliquid-docs/trading/funding)：按小时结算，HIP-3 的 funding 参数存在特殊设置；不能把参考基差当作跨所资金费完全抵消的证明。
- [Hyperliquid Auto-deleveraging](https://hyperliquid.gitbook.io/hyperliquid-docs/trading/auto-deleveraging)：ADL 可关闭对手方盈利仓位，双场所系统必须把外部仓位变化纳入恢复。
